# Layers clients immobiliers

## Composition

Une build sert un client, choisi par `GD_TARGET` ; aucun routage par `Host`.
Sans variable, le client historique `showcase-immobilier` est construit. Un
identifiant invalide, inconnu ou incohérent avec `site.ts` interrompt Nuxt.

`webapp/nuxt.config.ts` compose, dans cet ordre, `sites/<client>` puis `base`.
La première layer l’emporte. La racine utilise `base/` comme entrée technique
sans interface ; `base/nuxt.config.ts` déclare `app/` comme source du socle.
Les chemins historiques des composants, services et contrôles restent ainsi stables.
Les sources clientes vivent dans `sites/`, car Nuxt active automatiquement les
sous-dossiers de `layers/`.

| Périmètre                                     | Responsabilité                                                        |
| --------------------------------------------- | --------------------------------------------------------------------- |
| `app/`                                        | interface immobilière commune, pages, dashboard, stores et navigation |
| `app/app.config.ts`                           | réglages UI communs                                                   |
| `server/`, `services/`, `shared/`, `schemas/` | BFF, logique métier et contrats communs                               |
| `sites/<client>/app/app.config.ts`            | organisation, menus et surcharges de configuration                    |
| `sites/<client>/app/`                         | pages, composants et ressources propres au client                     |
| `sites/<client>/content/`                     | projection locale par langue                                          |
| `sites/<client>/public/`                      | fichiers servis sans transformation, dont `/images`                   |
| `sites/<client>/themes.yaml`                  | palettes et thèmes du client                                          |
| `sites/<client>/site.ts`                      | identifiant et nom par défaut de la build                             |

Les URL `/fr`, `/en`, `/es`, les endpoints et les parcours du dashboard sont
conservés. Le dashboard reste intégré à chaque instance ; il édite uniquement
la projection de son client. Les noms historiques `LogoShowcase*` désignent les
composants communs ; leurs SVG proviennent de `@site-assets/logo/`.

## Construire et déployer

Depuis `webapp/` :

```bash
GD_TARGET=showcase-immobilier bun run dev
GD_TARGET=showcase-immobilier bun run type-check
GD_TARGET=showcase-immobilier bun run build
node .output/server/index.mjs
```

`GD_TARGET` est transmis par Compose aux outils et comme argument de build Docker.
L’identité du serveur est compilée via `#site` : modifier `GD_TARGET` au démarrage
ne change pas le client servi. La sortie autonome embarque exclusivement ses
contenus et son thème dans `.output/site/<client>/`, et ses médias dans
`.output/public/`. Déployer le dossier `.output` complet.

`CONTENT_PATH` peut désigner une projection externe : lectures, écritures du
dashboard, setup et synchronisation utilisent le même chemin, sans repli vers un
autre client si le dossier manque. `CONTENT_SYNC_MEDIA_DIR` surcharge la destination
des médias synchronisés. Ces chemins explicites doivent appartenir au client déployé.
Les demandes de contact utilisent `.data/<client>/` par défaut.

Chaque client a sa propre instance, son environnement, son projet Symfony, son
secret de session, ses volumes et son domaine. Les variables `SITE_URL`, `SITE_NAME`
et les connexions existantes restent disponibles. Les fichiers `.env` sont préservés.
Pour les anciens déploiements, mettre à jour les chemins explicites
`CONTENT_HOST_DIR` et `MEDIA_HOST_DIR` vers les données déplacées ; les volumes
externes déjà affectés à un projet peuvent conserver leurs chemins. En développement,
Compose monte directement les dossiers de la cible sélectionnée.

`.nuxt` et `.output` restent les sorties historiques : construire les clients
successivement dans un même checkout. Utiliser des copies et piles distinctes pour
travailler ou construire simultanément. Git seul n’isole pas les services externes.

## Ajouter un client

1. Créer `sites/<identifiant>/nuxt.config.ts` et `site.ts` avec un identifiant
   identique au dossier et un nom. Reprendre la structure du client historique.
2. Fournir une configuration `organization` et `menu`, les fichiers de contenu
   nécessaires aux langues, `themes.yaml`, le favicon et les trois SVG de logo
   attendus dans `app/assets/logo/`. Adapter les textes et médias avant publication.
3. Ajouter uniquement les pages et composants qui diffèrent dans `app/` de la
   layer ; le même chemin surcharge le socle. Les pages Villa des Alizés restent
   exclusivement dans la layer historique.
4. Configurer un environnement et des volumes propres, préparer les contrats et
   contenus, puis exécuter types, tests, build et vérifications SSR pour cette cible.

Le socle ne doit importer aucun fichier client directement. Les données locales
non versionnées ont été déplacées avec le site historique ; elles ne se déduisent
pas d’un checkout neuf. Le setup de démonstration conserve ses protections contre
l’écrasement de données réelles.
